# SuppotInfo編集時の件数・対応番号の同期ルール

追加日: 2026-09-17。ユーザー指定の「SuppotInfoを増減したらSuppot_ChokuKisoCaseNoも数を合わせる」を、既存資料・NDU・保存処理を照合して共通ルールとした。

## 必ず揃えるもの

NDUの支点を編集して保存するときは、対象の周面・先端だけでなく、**対象外や他の拘束方向を含む全支点**について次を満たす。

```text
SuppotNum = SuppotRow = SuppotInfoの件数 = Suppot_ChokuKisoCaseNoの件数 = N
SuppotInfoのキー末尾番号             = 1～N（欠番・重複なし）
Suppot_ChokuKisoCaseNoのキー末尾番号 = 1～N（欠番・重複なし）
```

`SuppotInfo i` と `Suppot_ChokuKisoCaseNo i` は同じ支点項目番号で対応させる。節点番号・杭グループ番号とは区別する。たとえば `SuppotInfo61= ,122,2,...` に対応するのは `Suppot_ChokuKisoCaseNo61` であり、`...122` ではない。

`Suppot_ChokuKisoCaseNo61=0` の右辺は件数ではない。63支点になっても右辺を63へ一括変更しない。現物の杭周面・杭先端支点ではすべて0なので、このスクリプトが新規作成するケース行は `=0` とする。既存行の値は非0も含めて保持し、直接基礎のケース値の意味・付替えを推測しない。`ChokuKisoNum` や `ShitenCaseNum` を支点数に書き換える処理でもない。

## 増減・再採番の手順

- **追加:** `SuppotInfoN+1` を作ったら `Suppot_ChokuKisoCaseNoN+1=0` も作り、`SuppotNum`・`SuppotRow` を同時に更新する。
- **削除:** 削除する支点と同じ項目番号のケース行も削除する。途中の行を削除して番号を詰める場合は、残す支点とそのケース値を対にして同じ新番号へ移す。件数だけ合わせて別支点のケース値を流用しない。
- **0件:** `SuppotNum=0`・`SuppotRow=0` とし、両方の番号付きレコードを0件にする。`...0` というキーは作らない。
- **既存支点の値だけ更新:** 件数が変わらなくても、ケース行の欠落・余剰を残さない。整合済みのケース行は値・空白・改行を含めて保持する。

例: 周面60件から先端3件を追加すると、`SuppotInfo61～63` と `Suppot_ChokuKisoCaseNo61～63=0` を追加し、両件数を63にする。逆に末尾3支点を削除するときは、両方の61～63を削除し、両件数を60に戻す。

## スクリプトでの扱い

[`fill_suppot_info.py`](../../scripts/fill_suppot_info.py) の共通 `render_ndu()` が、支点編集の前後に `sync_ndu_support_cases()` を呼ぶ。[周面入力](fill-suppot-info-script.md)と[杭先端入力](fill-pile-tip-suppot-info-script.md)の両方に適用される。

1. 入力の `SuppotNum`・`SuppotRow` と実支点数、支点番号1～Nを検証する。これらの不整合は従来どおりエラー。
2. ケース行の重複、不正なキー番号、空欄・負数・非整数等の値はエラー。
3. 欠けたケース行を0で補う。実支点数を超える余剰行は値が0の場合だけ削除する。対応支点のない非0のケース行は、対応関係を判断できないためエラーにする。
4. その後に支点を追加・更新し、最終支点数に合わせてケース行を再同期する。追加前の検査により、元々余っていた非0のケース行が新規支点に引き継がれることも防ぐ。

ケース行が既にあればそのブロックへ補い、ない場合は実NDUに合わせて `G_intCHOKU_KISO_Link_Num` の後へ追加する。そのキーもなければ支点ブロックの後へ追加する。その他の行はバイト単位で保持する。

**現行の両CLIは支点の追加・更新を行うもので、支点の自動削除・再採番機能は持たない。** 周面抵抗0の節点に既存Y支点がある場合も、従来どおりエラーにする。同期関数は、既に支点と件数を減らした入力の余剰0ケース行を除去できるが、途中削除後の対応関係を推測して修復するものではない。削除機能を追加する際も上記の対による削除・再採番を必須とする。

## 現物確認と回帰検証

ルール追加時の読取り結果:

| 入力 | SuppotInfo | Suppot_ChokuKisoCaseNo | 確認事項 |
| --- | ---: | ---: | --- |
| snapの左右NDU | 各126 | 各126 | ケース行はすべて0 |
| 現在のtest右押しNDU | 63 | 63 | ケース行はすべて0、既に整合済み |
| testのbefore-suppotバックアップ | 0 | 0 | 支点追加前 |
| testのbefore-pile-tipバックアップ | 60 | 0 | 旧実装によるケース行の追加漏れ |
| testの`.ndu.bak` | 0 | 126 | 支点を減らしてもケース行が残った入力 |

旧実装は `SuppotNum`・`SuppotRow` だけを更新していたため、過去の「追加行と2つの件数変更以外を保持」という検証だけでは、この対応漏れを検出できなかった。過去の適用報告JSONは当時の記録として保持する。

回帰テストでは、追加、既存非0値の保持、欠落補完、件数減少後の余剰除去、0件、不正・重複・対応不明の非0行の拒否、再実行、両CLIへの適用、既存のNDU照合を確認する。Input-JR/JRSNAPでの読込み・解析実行は検証に含めない。

同期ルールを含むNDUの計算・保存・CLIの回帰テストを実行する。

```powershell
.venv\Scripts\python.exe -B -X utf8 -m unittest discover -s tests -q
```

実ファイルを使った別名の一時出力でも、支点0件→周面60件→先端追加後63件の各段階で、件数と対応番号が一致した。ケース行が欠けた60支点の旧バックアップからの出力も同じ63件のファイルとなった。0支点・ケース行126件のバックアップでは、余剰0ケース行だけが除去されることを確認した。snap/test原本は書き換えず、検証前後のSHA-256一致を確認した。
